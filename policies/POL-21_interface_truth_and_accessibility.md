# Truthful interface and accessible control

**Document ID:** POL-21  
**Package edition:** 1.0 / 2026-10-06  
**Document state:** WRITTEN_IMPLEMENTATION_SPECIFICATION  
**Implementation and runtime evidence:** NOT_STARTED / NOT_RUN in this delivered package.

## Scope and controlling responsibilities

Enforcement owner: desktop use cases + projections. This policy derives from the ground-up master prompt sections 32, 13. It is a complete written implementation rule; source adoption, exact compiled policy bytes and runtime enforcement require the build gates.

## Rules

Every enabled control MUST invoke a real use case and render actual state. Distinguish proposed, approved, dispatched, exited, observed and verified. A green badge cannot hide an unqualified model, broken identity or unresolved effect. Explain what is blocked and the smallest actionable resolution.

Preserve drafts, selected attachments and explicit settings through failure. Late callbacks are task/session-bound and cannot update a new view or restore revoked readiness. Keep long work off the UI thread, provide keyboard-accessible stop and never encode authority solely by color.

Ordinary conversation remains direct and proportionate. Audit details are inspectable without turning every answer into a governance report. First launch clearly discloses storage, observation scope, local-model choice and optional external access. No fake interface affordance may masquerade as a completed capability.

## Enforcement and evidence

Implement predicates at the stated control boundary and add rejection fixtures for each forbidden path. Record the exact policy version, inputs, evaluated rule IDs and result. The policy's text is not itself an executable guard. Preserve both a legal case and a boundary-violation case in the source-bound verification bundle.

## Change and exception handling

A conflict with current adopted source law blocks the affected activation and is entered in the decision register. Do not invent an exception to obtain a passing test. Proposed changes must preserve the audit trail, identify impacted requirements and re-run dependent tests. Emergency responses may only exercise pre-existing, narrower authority.
