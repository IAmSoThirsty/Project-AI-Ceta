## Scope and controlling responsibilities

Enforcement owner: capture adapter + action broker + trusted approval. This policy derives from the ground-up master prompt sections 33. It is a complete written implementation rule; source adoption, exact compiled policy bytes and runtime enforcement require the build gates.

## Rules

Voice, selected-screen capture and additional interfaces MUST use the same identity, context, authority and evidence contracts as text. Capture begins only through explicit activation with visible status and clear device/scope. Recognition uncertainty remains an observation quality issue, not automatic authorization.

A spoken ambiguity affecting target or consequence requires the smallest necessary confirmation. A browser page, tool response or displayed text cannot issue commands merely because it is visible to a model. External actions bind exact recipient, destination, content and scope; scheduling requires durable runtime acceptance.

Physical actuation requires real interlocks, device identity, completion feedback and hardware qualification. Hardware unavailable during development stays in the requirement register with its activation gate closed. Simulated actuators prove simulated contracts only. Text-only workflows remain usable without capture devices.

## Enforcement and evidence

Implement predicates at the stated control boundary and add rejection fixtures for each forbidden path. Record the exact policy version, inputs, evaluated rule IDs and result. The policy's text is not itself an executable guard. Preserve both a legal case and a boundary-violation case in the source-bound verification bundle.

## Change and exception handling

A conflict with current adopted source law blocks the affected activation and is entered in the decision register. Do not invent an exception to obtain a passing test. Proposed changes must preserve the audit trail, identify impacted requirements and re-run dependent tests. Emergency responses may only exercise pre-existing, narrower authority.
