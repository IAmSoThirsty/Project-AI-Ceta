## Scope and controlling responsibilities

Enforcement owner: lead integrator + independent verification. This policy derives from the ground-up master prompt sections 39, 40, 41, 42. It is a complete written implementation rule; source adoption, exact compiled policy bytes and runtime enforcement require the build gates.

## Rules

Implementation MUST preserve the complete mission while proceeding through bounded work packages. Source inspection, architecture, code, tests, repair and installed qualification are separate evidence states. Documentation completion and a passing package checker do not mark a runtime capability complete.

Allocate one lead integrator and real scoped workers. Do not invent reviewers, overwrite concurrent work, drop historical defects or declare unavailable hardware tests passed. Each change retains source/requirement/test links and a checkpoint another agent can continue from.

A blocker names its observed cause, affected dependencies, exact needed decision/resource and safe work that continues. Difficulty alone is not a blocker. Production cutover and publication remain reserved gates. Report written, implemented, executed, independently reviewed, installed-qualified and elapsed-time results separately, with failed/skipped/not-run evidence intact.

## Enforcement and evidence

Implement predicates at the stated control boundary and add rejection fixtures for each forbidden path. Record the exact policy version, inputs, evaluated rule IDs and result. The policy's text is not itself an executable guard. Preserve both a legal case and a boundary-violation case in the source-bound verification bundle.

## Change and exception handling

A conflict with current adopted source law blocks the affected activation and is entered in the decision register. Do not invent an exception to obtain a passing test. Proposed changes must preserve the audit trail, identify impacted requirements and re-run dependent tests. Emergency responses may only exercise pre-existing, narrower authority.
