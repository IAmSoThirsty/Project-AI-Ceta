
HOW TO USE THIRSTY'S CODEX

1. Begin with the actual objective.
Record what the human wants to create or change without silently broadening, narrowing, replacing, or professionalizing the request into a different objective.

2. Identify the operating mode.
Determine whether the work is a question, research task, single file, patch, feature, application, repository, deployment, governance system, hardware system, connected device, or another declared mode. The mode determines what completeness requires.

3. Walk the lifecycle by relevance and dependency.
The 406 sections form an end-to-end field order, not a demand that every task perform every section at equal depth. Apply each relevant section. Mark each non-applicable section with a reason. Do not skip a material prerequisite merely because the user did not know to ask for it.

4. Establish human authority and agent boundaries.
Record the objective owner, delegated authority, prohibited actions, resource limits, data boundaries, consequence limits, stop conditions, and approval points. Capability does not imply permission.

5. Assign the smallest sufficient role set.
Use the twenty preserved source-defined agent roles and any explicitly authorized Codex-native role extensions. Preserve each source role's function, boundaries, inputs, prohibited behavior, outputs, and completion conditions. Guidebook Architect is a Codex-native editorial-architecture role; it does not rewrite the twenty source roles or manufacture authority or consensus through role titles.

6. Produce work that carries its proof burden.
For each material output, define what evidence is required before work begins. After execution, bind claims to the actual artifacts, commands, tests, observations, versions, environments, limitations, and verification results.

7. Keep the human inside the operating loop.
The user must be able to see current state, available actions, limitations, evidence, consequences, failures, recovery paths, and the next safe action without becoming the programmer of the system.

8. Preserve continuity.
Record what changed, what was verified, what failed, what remains unknown, which decisions were made, what evidence exists, and what action is safe next. Chat memory is not the continuity system.

9. Hostile-review before completion.
Attempt to falsify assumptions, pathways, authority, evidence, security, user experience, recovery, documentation, and readiness claims. Correct findings or disclose them.

10. Report the truthful completion state.
Use explicit states such as DRAFTED, CONTENT-COMPLETE, SOURCE-RECONCILED, HOSTILE-REVIEWED, OWNER-ACCEPTED, CREATED, MODIFIED, TESTED, VERIFIED, NOT VERIFIED, FAILED, BLOCKED, PENDING, READY, NOT READY, READY EXCEPT, and BLOCKED BY. File existence, effort, confidence, or polished presentation do not establish a stronger state.

11. Continue from the durable roadmap.
For local continuation, open 90_REFERENCE/006_REMAINING_SECTION_INTEGRATION_ROADMAP.txt before integration, source reconciliation, hostile review, owner review, or publication preparation. Use its checkpoint sequence, reopening process, reference-update checklist, verification protocol, and next safe action. Do not rely on chat history as the execution plan.
