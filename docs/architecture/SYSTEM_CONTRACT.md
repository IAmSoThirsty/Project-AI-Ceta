## Product and operating boundary

CETA is the native Windows-first product and delivery identity for the Project-AI intelligence-system objective. The intelligence operating system manages cognition, context, memory, authority, work and evidence above the host operating system. Its initial deployment is one local application with deliberately isolated helpers and a single supported production entry point. A bootable replacement kernel, remote-host administration and a new cloud dependency are not part of this delivery contract.

The owner chooses objectives and grants bounded authority. The Companion deliberates and communicates. The deterministic kernel owns admissible transitions and positive authority. Adapters act, independent observers inspect resulting reality, and the kernel settles the outcome. The Fates and graph make relevant history available to later reasoning without making memory an alternate governor.

## Canonical planes

The evidence plane records observations and lineage; the cognition plane forms interpretations and proposals; the authority plane admits exact permitted actions; the effect plane performs them; the verification plane inspects outcomes; the continuity plane rebuilds the current usable account. These are responsibilities with explicit contracts, not automatically six deployable services. Separation becomes a real OS or administrative boundary wherever the security claim depends on it.

Each project has its own isolation scope, ordered history and current projections. Shared installation metadata contains only information authorized across scopes. A cross-project task names both scopes and the bridge grant. A distributed CBCC domain retains its own independent decision history; one local journal cannot pretend to be the administrator of every domain.

## Object ownership

`contracts` owns shapes and canonicalization, `kernel` owns policy and transitions, `store` owns persistence mechanisms, `identity` supplies authenticated actor/time evidence, and `supervisor` owns controlled work lifetimes. `observation`, `context`, `memory` and `companion` create scoped evidence or cognitive products. `effects` performs admitted work; `verification` supplies outcome findings. Custody and threshold authority use their own declared trust boundaries, with kernel requests rather than unrestricted key sharing.

No projection, UI callback, retrieved document, role prompt, graph label or receipt can mint authority. All positive grants and settlements are derived from current canonical state under accepted policy. A module may request a transition only through its typed port and must preserve the denial it receives.

## Complete operating journey

A trusted user interaction creates a task and finite observation scope. The supervisor admits a subscription, and observation workers read only authorized resources. The compiler constructs current context, including contradictions, source revisions, permissions and omitted material, and hands an exact prepared request to the qualified owned model. The model returns an untrusted answer or action proposal.

A material action is translated into bounded IR, staged where applicable and reviewed against exact candidate and policy identities. Authentic consent and the required review evidence enter the kernel, which checks current state, reserves budgets and commits intent. The broker redeems the one-use permit at the defined admission boundary, performs the bounded effect, and returns process evidence. A separate observation checks actual postconditions. Settlement updates dependent state and relevant memory; the next session reconstructs this account rather than replaying the effect.

## Continuous participation

Presence is event-driven. The supervisor remains available under the user's selected running/background policy; models wake for admitted tasks rather than consuming infinite inference in an idle loop. Unfinished tasks, questions, obligations, rejected alternatives and observations survive through records. Observational gaps are explicit and reconciled after downtime. The first full-system acceptance journey uses one selected fixture workspace but exercises every applicable boundary.

## Required engineering split

A code module is not a trust domain. The initial Python/PySide6 host must not hold universal worker credentials or expose arbitrary execution endpoints. A small qualified native boundary supplies Windows handle, IPC, containment and secret-lifetime controls where required. The exact native language and supported toolchain are chosen by a recorded engineering decision after inspection, not independently by each worker. Production composition is explicit and acyclic; no parallel legacy authority path remains after cutover.

## Acceptance boundary

The written contract is usable as the build baseline. Formal source conformance, executable protocol enforcement and product qualification are separate gates. The complete build preserves all agreed capabilities while closing only the activation lanes whose required assumptions cannot yet be demonstrated. A narrow qualified profile and full mission completion remain distinct status fields.
