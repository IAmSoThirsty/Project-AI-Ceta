## Component and subsystem tests

| Component | Integrated behavior | Invariant |
| --- | --- | --- |
| [19.01](19.01-STATE-REGISTER/README.md) | Define canonical records; validate expected versions and allowed transitions; commit state and event references; expose consistent reads and historical views. | Each authoritative state record has one owning service and versioned update semantics. |
| [19.02](19.02-DURABLE-STORAGE/README.md) | Open qualified local storage; validate schema and integrity; execute bounded transactions; commit state and publication intent atomically; recover after interruption. | A successful API return follows the configured durable commit boundary. |
| [19.03](19.03-SNAPSHOTS/README.md) | Capture a consistent state boundary; write content and manifest; verify completeness; register a usable snapshot; retain and retire according to approved policy. | A snapshot includes its consistency point and cannot claim newer effects or revocations it never observed. |
| [19.04](19.04-RECOVERY/README.md) | Inspect actual persisted state and effects; choose a validated recovery point; reconcile later observations; restore data; reauthenticate and requalify before resuming tasks. | Recovery preserves conversations, identity records, unsent drafts, and uncertain-operation evidence unless an explicit authorized repair requires otherwise. |
| [19.05](19.05-MIGRATION/README.md) | Plan compatibility and data transformations; run preflight and backup; stage or checkpoint migration; validate transformed data; commit activation; verify rollback or forward repair. | Migration success includes preserved user data and working application behavior, not only a new schema version. |
| [19.06](19.06-ARCHIVAL/README.md) | Archive selected history with provenance and retention labels; validate exports; index permitted metadata; reconstruct authorized historical views without reactivating past authority. | Historical records are inspectable evidence and never executable permission grants. |
