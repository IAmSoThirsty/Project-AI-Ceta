## Component and subsystem tests

| Component | Integrated behavior | Invariant |
| --- | --- | --- |
| [23.01](23.01-TEST-ARCHITECTURE/README.md) | Register requirements and test oracles; build controlled fixtures; execute on pinned source and environment; normalize results without erasing failures or omissions. | Every test has an observable oracle independent of the implementation claim it evaluates. |
| [23.02](23.02-CONTRACT-TESTING/README.md) | Exercise canonical schemas and semantics on producers and consumers; test valid, invalid, stale, and adversarial inputs; bind results to exact contract revisions. | Passing schema validation alone does not establish semantic compatibility. |
| [23.03](23.03-INTEGRATION-TESTING/README.md) | Execute complete workflows across real subsystem boundaries; observe effects independently; interrupt at defined points; validate state, authority, and evidence continuity. | Mocks may isolate units but cannot replace all installed-runtime boundary tests. |
| [23.04](23.04-ADVERSARIAL-AND-FAILURE-TESTS/README.md) | Construct bounded adversarial inputs and faults in isolated fixtures; attempt declared boundary violations; observe enforcement; preserve reproducible failures and recovery evidence. | Adversarial tests run only against owner-authorized isolated targets. |
| [23.05](23.05-PRODUCT-QUALIFICATION/README.md) | Collect current results; validate source and environment binding; evaluate mandatory gates; preserve existing local acceptance obligations; approve release only with complete evidence. | Existing local gates are reconciled and retained unless an explicit approved change replaces them. |
| [23.06](23.06-USER-EXPERIENCE-TESTING/README.md) | Test real owner workflows through the native interface; inspect focus and assistive behavior; measure performance under representative load; verify state and evidence outcomes. | Visual appearance and screenshot similarity do not establish functional correctness. |


Run these flows through actual local implementations after unit tests. Bind results to exact source, dependencies, configuration, environment, and artifact bytes. A mock-only test cannot qualify a native enforcement or installed-product claim. Preserve failed, blocked, skipped, and not-executed cases separately. Use [the cross-system scenarios](../ACCEPTANCE-CRITERIA/END-TO-END-SCENARIOS/README.md) for user-workflow qualification.
