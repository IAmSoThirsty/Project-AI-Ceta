## Component and subsystem tests

| Component | Integrated behavior | Invariant |
| --- | --- | --- |
| [00.01](00.01-PRODUCT-IDENTITY/README.md) | Load the approved product baseline; resolve amendments; expose a versioned invariant set; make every change traceable to an owner decision. | Product scope changes require a recorded decision and affected acceptance criteria. |
| [00.02](00.02-SYSTEM-TOPOLOGY/README.md) | Register components; validate unique ownership; distinguish build, runtime, data, and optional dependency edges; expose navigation and impact analysis. | An optional integration never becomes a prerequisite for the local baseline. |
| [00.03](00.03-RUNTIME-LIFECYCLE/README.md) | Initialize minimum storage and trust prerequisites; activate policy and dispatch boundaries; advertise readiness; stop admission; drain or terminate work; close durable stores. | No effectful operation starts before its required authority and evidence services are ready. |
| [00.04](00.04-INTEGRATION-BASELINE/README.md) | Inspect only the selected local root; capture a read-only baseline; map logical units to observed files; resolve collisions; approve reuse or extension before editing. | The source path is established by local inspection, never inferred from a remote project. |
| [00.05](00.05-ARCHITECTURE-ASSURANCE/README.md) | Evaluate graph structure, invariant coverage, and contract ownership against the same baseline; produce findings before integration approval. | A passing structural check never stands in for runtime qualification. |


Run these flows through actual local implementations after unit tests. Bind results to exact source, dependencies, configuration, environment, and artifact bytes. A mock-only test cannot qualify a native enforcement or installed-product claim. Preserve failed, blocked, skipped, and not-executed cases separately.
