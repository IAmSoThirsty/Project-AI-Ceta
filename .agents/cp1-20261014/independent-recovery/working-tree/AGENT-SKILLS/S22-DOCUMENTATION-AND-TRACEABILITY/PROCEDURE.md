# S22 procedure

## Goal

Current file, contract, operation, migration, and release guidance with validated links.

## Domain-specific sequence

1. Trace requirements to files and tests. For this step, preserve the exact input references, decision rationale, and output evidence required by the assigned unit.
2. Describe actual behavior. For this step, preserve the exact input references, decision rationale, and output evidence required by the assigned unit.
3. Identify exact evidence. For this step, preserve the exact input references, decision rationale, and output evidence required by the assigned unit.
4. Preserve local integration decisions. For this step, preserve the exact input references, decision rationale, and output evidence required by the assigned unit.
5. Validate references and examples. For this step, preserve the exact input references, decision rationale, and output evidence required by the assigned unit.
6. Label proposed and observed work separately. For this step, preserve the exact input references, decision rationale, and output evidence required by the assigned unit.

## Integration and evidence

Apply the mapped local application's existing language, architecture, and qualified facilities. Keep one canonical owner for authority, state, evidence, and resource admission. Record expected versus observed outcomes at each consequential boundary. Use independent oracles rather than merely reproducing the implementation's assumptions. Preserve failed checks and unresolved effects for the receiver.

## Stop conditions

Stop the affected operation when authority expires, scope changes, source preconditions fail, required enforcement is unavailable, or evidence indicates an uncertain external effect. Inspect and reconcile before retrying. Do not erase data or weaken controls to make progress appear successful.

## Completion check

A reader can navigate requirement to implementation to test to evidence without invented references.

Before handoff, construct and evaluate the adverse fixture: A completion report claims work solely because it appears in a plan. The final report must identify the actual test state rather than implying a test ran because this procedure describes it.
