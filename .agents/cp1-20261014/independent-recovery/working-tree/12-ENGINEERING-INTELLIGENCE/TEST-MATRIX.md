Every source specification defines ten concrete test obligations: required behavior, a domain-specific adverse case, schema compatibility, stale references, access, bounds and interruption, concurrency, recovery, real integration, and independent proof. These are planned tests, not runtime results.

## Component and subsystem tests

| Component | Integrated behavior | Invariant |
| --- | --- | --- |
| [12.01](12.01-PROJECT-DISCOVERY/README.md) | Inspect the selected project; identify languages and entry points; index source and dependencies; report unknown generated or binary content; bind findings to a source snapshot. | Project knowledge is invalidated when the underlying source revision changes. |
| [12.02](12.02-ENGINEERING-PLANNING/README.md) | Trace each requirement to current behavior; define target changes and tests; sequence dependencies; assess effects and migration; request approval for changed scope. | Planning cannot silently redefine product completion or remove difficult acceptance criteria. |
| [12.03](12.03-CODE-CONSTRUCTION/README.md) | Plan exact edits against inspected source; stage coordinated changes; validate ownership and preconditions; apply through governed file operations; inspect the resulting diff. | Implementation edits preserve unrelated owner changes and never assume an empty project. |
| [12.04](12.04-TESTING-AND-DEBUGGING/README.md) | Reproduce the reported behavior; establish a failing test; inspect logs and state; propose a bounded repair; rerun targeted and affected regression tests. | A repair is accepted only when the original failure is reproduced and the corrected behavior is observed, or the reproduction gap is explicitly unresolved. |
| [12.05](12.05-ENGINEERING-REVIEW/README.md) | Inspect exact changes; compare against contracts and requirements; reproduce critical tests independently; classify findings; approve or return changes with evidence. | Independent review must inspect the actual proposed revision and cannot approve by trusting the builder summary. |
| [12.06](12.06-ENGINEERING-DELIVERY/README.md) | Build from the pinned source; run verification; reconcile documentation and interfaces; report exact deliverables and unresolved obligations; hand off to product qualification. | A successful compile alone cannot establish installed product completion. |


Run these flows through actual local implementations after unit tests. Bind results to exact source, dependencies, configuration, environment, and artifact bytes. A mock-only test cannot qualify a native enforcement or installed-product claim. Preserve failed, blocked, skipped, and not-executed cases separately. Use [the cross-system scenarios](../ACCEPTANCE-CRITERIA/END-TO-END-SCENARIOS/README.md) for user-workflow qualification.
