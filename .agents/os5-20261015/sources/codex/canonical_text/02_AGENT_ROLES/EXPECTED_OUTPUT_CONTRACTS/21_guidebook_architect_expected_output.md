## Guidebook objective and audience

Objective: propose a navigable guidebook architecture that helps Vibe Coders move from an idea to governed research, design, implementation, operation, recovery, and retirement while keeping human authority and evidence visible.

Primary audience: Vibe Coder using natural-language and AI-assisted tools. Secondary audiences: accountable owner, technical reviewer, educator, maintainer, and agent operator. No external reader research is supplied in this fixture.

## Scope and corpus baseline

Scope: front matter, shared governance, twenty source-defined role files, one Codex-native guidebook role, expected-output contracts, 406 lifecycle sections, source register, glossary, index, cross-reference register, continuity records, and publication aids. The fixture does not establish that every file is current, reconciled, reviewed, verified, accepted, or ready for PDF distribution.

Baseline identity: synthetic snapshot `GUIDEBOOK-FIXTURE-01`; source versions, file hashes, and effective dates are illustrative and must be replaced by live evidence.

## Proposed information architecture

1. Orientation: purpose, audience, how to use the guide, lifecycle map, status language, glossary, and index.
2. Governance: human intent, authority, evidence, continuity, owner control, and safe interaction.
3. Workforce: preserved role definitions, expected-output contracts, Codex-native extensions, assignment boundaries, and handoffs.
4. Lifecycle: the 406 domain sections, applied by relevance and dependency rather than mechanically at equal depth.
5. Reference: source register, cross-reference register, integration checkpoints, unresolved gaps, and continuity.
6. Publication: navigation, citations, diagrams, accessibility, version, rendering, package identity, and acceptance record.

## Reader pathways

- New Vibe Coder: Orientation -> human authority -> assign roles -> choose relevant lifecycle sections -> produce evidence -> review -> hand off.
- Quick task: objective -> mode -> applicable sections -> role assignment -> evidence and stop conditions -> bounded output.
- High-consequence work: authority -> research -> requirements -> architecture -> security, safety, privacy, and accessibility -> testing -> verification -> acceptance -> operations and recovery.
- Review work: exact claim -> scope and evidence -> Critic, Security Auditor, Tester, Verifier, Governance Reviewer, or UX Reviewer -> bounded finding -> owner decision.
- Recovery or retirement: current state -> incident or lifecycle boundary -> preservation -> recovery, migration, decommissioning, disposal, or retirement -> continuity.

These pathways are proposed navigation, not evidence that each reader can complete the journey without user research or usability testing.

## Dependency and placement decisions

The role contract belongs in the workforce layer and must remain visibly separate from the twenty imported source-defined roles. The 406 sections belong in the lifecycle layer and define domain work, not agent identity. Shared governance controls both layers. The Guidebook Architect proposes the relationships; the owning role or human authority resolves domain truth, policy, source, and acceptance questions.

Concept placement examples: define `human authority` in shared governance and cross-reference it elsewhere; define each lifecycle discipline in its numbered section; define the expected role output in the corresponding contract; keep examples and commentary labeled as such; retain source disagreements in the source or unresolved-gap register.

## Evidence and verification plan

Verify every link and destination in the navigation map; confirm section and role identifiers; inspect that source and synthesis labels remain visible; test retrieval of a reader pathway from a clean copy; run accessibility and reflow review on the rendered artifact; independently compare publication metadata with the accepted source tree; and obtain human owner acceptance for the exact package identity.

## Findings, limitations, and completion assessment

The bounded completion state is `Proposed`; the guidebook is not claimed to be complete, accepted, or published.

## Reject the output when it contains

- A guidebook map presented as proof that the content is true or complete.
- Source-defined roles and Codex-native roles merged without provenance.
- Reader needs invented without evidence or labeled assumptions.
- A section count, word count, link check, page count, or rendered PDF used as proof of content acceptance.
- Missing prerequisites, high-consequence paths, failure, recovery, accessibility, or owner control hidden for readability.
- Specialist disagreement or unresolved source gaps removed from the reader path.
- Publication, owner acceptance, verification, or source reconciliation claimed without the required evidence.
